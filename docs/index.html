Install & run

  1. Download the installer (or the portable ZIP) above.
  2. Run it — installs per-user, no administrator rights needed.
  3. Launch Mulvakun, pick Tor or Proxies, then Connect.
  4. For Tor, optionally choose an exit country under the Connect button.
  5. Closing the window while connected minimizes to the system tray.

Get Tor bridges (when Tor is blocked)

If your network blocks Tor, you need bridges — unlisted entry points. Ask the Tor Project for a few lines (obfs4, webtunnel or snowflake) using any of these, then paste them into Mulvakun.

Website bridges.torproject.org — open Advanced Options, choose obfs4 or webtunnel, solve the captcha, copy the lines.
Telegram bot @GetBridgesBot — send /start, then /bridges to get obfs4 bridges.
Email Mail bridges@torproject.org from Gmail/Riseup with body get transport obfs4. Reply contains the lines.

Add them in Mulvakun

  1. Open Settings (the ☰ button, top-right).
  2. Paste the bridge lines into “Tor bridges (one per line)” — one per line, exactly as given.
  3. Click Save, then choose Tor and press Connect.

A bridge line looks like: obfs4 12.34.56.78:443 <FINGERPRINT> cert=… iat-mode=0  ·  supported types: obfs4, webtunnel, snowflake, meek, conjure (and plain). Leave the field empty for a direct Tor connection.

Fix: LAN sharing stopped working (Windows)

Symptom: Mulvakun connects fine on the PC itself, but other devices on the network can no longer use it as a proxy — they just time out. Typically it worked right after install and stopped later, after an update or a reboot.

This is not a lost Mulvakun setting. The proxy port is opened by the bundled engine process bin\sing-box.exe, not by mulvakun.exe — so a firewall “allow” granted to Mulvakun itself does nothing for LAN traffic. Windows Firewall is blocking inbound connections to that engine.

1. Confirm the cause

In Mulvakun open Settings → Proxy availability and check that Whole LAN (0.0.0.0) is selected. Then, in Command Prompt:

netstat -ano | findstr :2080

You want a line reading TCP 0.0.0.0:2080 … LISTENING. The 0.0.0.0 means the port is bound for the whole network and the app is configured correctly — so anything still failing is the firewall. If it says 127.0.0.1:2080 instead, switch to Whole LAN in Settings and reconnect. Substitute your own port if you changed it from 2080.

2. Apply the fix

Open PowerShell as Administrator (Win+X → Terminal (Admin) or PowerShell (Admin)) and run:

Get-NetFirewallApplicationFilter |
  Where-Object { $_.Program -like "*sing-box.exe" } |
  Get-NetFirewallRule | Where-Object { $_.Action -eq 'Block' } | Remove-NetFirewallRule

New-NetFirewallRule -DisplayName "Mulvakun LAN proxy" `
  -Direction Inbound -Action Allow -Protocol TCP `
  -LocalPort 2080 -RemoteAddress LocalSubnet -Profile Any

The first command removes a Block rule if one exists — Windows silently creates one when the firewall consent dialog is dismissed with Cancel, and Block always beats Allow, so the port then stays shut permanently. The second command opens the port. Keep -RemoteAddress LocalSubnet: the local proxy has no authentication, so it must never be reachable beyond your own network. This rule is bound to the port rather than to a file, so it survives app updates.

3. Verify from another device

Test-NetConnection 192.168.X.Y -Port 2080

TcpTestSucceeded: True means it works — point the other device's proxy settings at that IP and port. Use the PC's own LAN address, which Mulvakun shows under the Connect button while connected.

4. Still blocked? Check the network profile

Get-NetConnectionProfile | Select-Object Name, NetworkCategory

If NetworkCategory is Public, Windows treats your home network as untrusted and firewall rules scoped to the private profile stop applying. Windows can flip this back to Public on its own after an update or a router change — which is exactly why LAN sharing “worked yesterday” and then didn't. Set it back with:

Set-NetConnectionProfile -InterfaceAlias "<Name from the output above>" -NetworkCategory Private

Which systems this affects

Any Windows build can hit this, but it is far more likely on some:

Most likely Debloated / “lite” builds: Tiny10, Tiny11, TTSC, AtlasOS, Ghost Spectre, LTSC images. Removed components mean the firewall consent dialog often never appears, so the port is silently never allowed.
Sometimes Windows 10/11 Home and any fresh install, when the consent prompt was dismissed with Cancel, or when the network is marked Public. Also common with third-party firewalls (Kaspersky, ESET, Comodo) — allow the port there instead.
Rarely Windows 10/11 Pro / Enterprise on a normal install — the prompt usually appears and the rule persists. Managed machines are the exception: domain Group Policy can override or delete local firewall rules.

Linux users: Mulvakun detects ufw / firewalld and offers an “Open port in firewall” button in Settings, so no manual step is needed there.
